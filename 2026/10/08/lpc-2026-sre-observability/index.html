二、主线一：健康度要能解释用户体验与发布结果

2.1 从单点阈值，转向跨发布阶段的可比较性

Meta 的 slides 区分了绝对健康告警与新旧内核之间的相对健康检查。困难在于新旧版本的主机数量相差多个数量级，crash、stall、lockup 等稀有事件在短窗口内又存在明显的离散性。官方 Slides，p.4、6–12

其处理方法是把“某台主机在某时间窗内是否发生事件”视作 Bernoulli 试验，在主机多、单机事件概率低的条件下使用 Poisson 近似。数据可以按时间、主机或两者分桶；检查方差／均值 φ 是否合理，再拟合成熟内核数据，并把分布换算到新内核的主机规模，以判断新版本是否显著更差。官方 Slides，p.13–17

slides 同时列出适用条件：各桶需要统计可比，新旧版本之间影响事件概率的外因也要处理，例如日内工作负载变化，以及新内核刚上线导致 uptime 较短。官方 Slides，p.18

对 SRE 的启示：灰度阶段比较低频故障，应把样本规模、工作负载、硬件、运行时长和分桶方式纳入判断。迁移到设备端时，先验证这些假设，再选择统计模型与告警阈值。

2.2 内核事件必须连接用户可见结果

小米团队在 Pixel 6、6.18.0-mainline、90 Hz 的指定环境中分析了 40 个 Android 应用，把 lock_contention 与 Perfetto FrameTimeline 关联。作者报告：约 14% 的掉帧可归因于内核锁竞争，且五类热点占锁相关掉帧的 90% 以上，涉及 GPU 驱动、mmap_lock、ZRAM、Binder 分配器和 cgroup 锁。官方摘要

这里最值得迁移的方法是：从用户症状窗口反查关键线程的等待，再定位依赖对象。 但上述比例属于作者报告的特定实验，不应写成所有 Android 设备的普遍结论；事件在时间上重合后，还需通过干预或复现验证因果关系。

Wattson 的议题则把 Perfetto trace 与按 SoC 建模的 CPU 功耗估计用于内核回归测试。官方摘要它补充了一个容易被忽略的质量维度：响应更快的修改也可能增加功耗。这里的功耗是模型估计，应通过硬件仪器测量校准；GPU、TPU/NPU 属于作者提出的扩展方向。

2.3 长时间测量仍不可替代

OSADL QA Farm 的报告强调长期、跨系统可比较的实时延迟测量，并讨论测试场景随 Linux 和硬件演化而调整。官方摘要

本文判断：这与“模型更强，所以过程数据可以无限削减”的想法构成重要制衡。模型可以帮助解释罕见延迟，但测量窗口、测试负载、硬件差异及尾部分布仍需真实采集。评价长尾风险时，应保留测量时长与负载覆盖范围。

三、主线二：观测预算必须同时计算采集、关联、保存和恢复成本

3.1 大型转储暴露的是诊断经济性问题

CoreWeave 的 slides 描述了 2–4 TB 内存的大型节点：默认单线程 makedumpfile 可能耗时 20–60 分钟，恢复速度与故障证据都直接影响运营。官方 Slides，p.2

第 3 页给出了当前运行流程，据此更新初版摘要中的“指纹去重开发中”状态：

  1. panic 后进入精简 crash kernel，启用 4 个 CPU。
  2. 挂载保存已知 panic 指纹数据库的文件系统，并匹配当前 panic 栈指纹。
  3. 命中已知指纹时保存 dmesg，跳过 dump；未知故障使用多线程 makedumpfile 采集后重启。
  4. 使用 16 个以上 CPU／线程向对象存储上传 dump。

指纹基于 panic 栈及寄存器值、错误信息等周边数据。AI 根因分析单独讨论；作者在第 6 页指出幻觉仍妨碍将 AI 用于故障分类／去重。第 9 页把 DPU 上经 RDMA 使用 drgn 读取运行内核列为探索，并提出安全性和生产实践问题。官方 Slides，p.3、5–6、9

对 SRE 的启示：先识别已知故障，再选择采集深度，可减少重复转储。设备端实验应同时衡量恢复耗时、指纹误匹配、已知故障变体漏检和保留证据的诊断能力；这些是迁移方案需要验证的指标。

3.2 BPF 快照：把诊断请求变成有界采集

BPF 快照提案以在线内核中的任务、D-state 栈、runqueue、reclaim 和 I/O 状态为对象，探索经过预先约束的内核内遍历与紧凑输出。作者同时把 iterator、helper/kfunc、verifier、输出缓冲和不停机情况下的一致性保证列为讨论问题。官方提案

它提供了值得试验的在线状态采集设计点。本次检索中该议题仍未排期，也未确认可读的公开性能测量正文。

迁移建议：为每种采集器定义最大对象数、耗时、输出字节数及失败行为。达到限额时应报告 truncated、丢弃计数和有效时间区间，让分析器能识别信息缺口。

3.3 小记录不等于小系统成本

Build ID + offset sampling 比较了直接记录文件身份和偏移，与记录虚拟地址后再依赖映射事件完成符号化的取舍；目标包括讨论混合采样方式。官方摘要

栈记录议题则讨论重复栈挤占缓冲区、栈合并及用户态栈的文件关联问题。官方摘要两者共同提醒我们：压缩单条事件，不一定能减少整套证据系统的开销；关联元数据、映射生命周期和重复记录同样占预算。

3.4 低扰动工具要能进入真正的故障现场

生产 RT tracepoint 议题提出将抢占／IRQ 开关事件从较重的设施中拆开，通过独立配置与 static key 控制启用。官方摘要perf/ftrace 互通议题则尝试复用同一份采集数据，减少为统计分析和时间线分析重复录制。官方摘要

这些工作的共同价值是降低“只能在实验室开启”的门槛。但补丁提案、已排期演讲、内核已合入和发行版可用，是四个不同状态，应分别记录；实际开销需要在目标负载下测量。

四、主线三：比日志数量更重要的是关联键、生命周期和等待关系

4.1 故障报告应有同一次启动的时间线

统一内核故障报告提案关注 dmesg、syslog、devcoredump 和 sysfs 信息分散、采集延迟及环形缓冲区覆盖。它建议在问题发生时自动采集，并在服务端按 session／boot 关联、匹配已知问题和通知相关维护者；非致命问题可能在稍后级联成更严重故障。官方摘要

对长时间故障的启示：最终 crash log 应与先前关键事件配合，借助时间和身份信息连接故障过程。实际落地还需明确脱敏、用户授权、保留期限，以及跨设备标识是否可被关联；这属于本文补充的部署要求。

4.2 per-skb metadata：身份应跟随被观测对象

Cloudflare 的包路径追踪尝试在 netns、隧道、IPsec 和过滤规则之间保留同一数据包的路径。摘要指出，用外部 BPF map 保存旁路状态需要维护释放清理，而这可能使只关心少量包的采样器仍承担大量包的生命周期事件成本；其上游探索是让 metadata 随 sk_buff 生命周期存在。官方摘要

这比“给每条日志加一个 ID”更深一层：身份的创建、传播、变换和销毁本身就是观测机制的一部分。

映射到设备端，可以借鉴这一问题意识来设计 Binder transaction、异步任务或请求对象的关联信息。不过，复用地址、对象克隆和跨进程身份如何处理，需要根据各子系统的对象语义独立定义。

4.3 从锁顺序，扩展到通用等待／事件依赖

DEPT 关注等待和事件的关系，而不仅是传统锁的获取顺序，覆盖 completion、folio lock、DMA fence 等同步模式。作者把误报及子系统注解不足明确列为推进工作的难点。官方摘要

持锁者无法运行的 fleet 调查也说明，只看等待线程不够，还需要追踪被等待对象及其拥有者的可运行状态。官方 session 摘要

本文判断：等待图的可解释性来自能够核查的依赖关系。边必须有来源和语义，例如“线程 A 在等事件 E”“任务 B 负责产生 E”；缺少关联或注解时，应保留未知状态。

五、主线四：AI 改变诊断的入口，但不替代测量与调试工具

5.1 Performance prompts：维护的资产不再只有工具代码

Brendan Gregg 将 prompt、skill 和 agent 放进性能分析流程，并讨论如何让 flame graph、eBPF、ftrace 等工具适合 AI 使用。第 15 页比较 PNG、SVG 与原始采样文本在效果、主机开销、Token 成本、可重复性及人工复核上的取舍；作者提出可以探索细节量介于 PNG 与 SVG 之间的 JSON 摘要。第 22 页进一步要求工具输出既保留诊断细节，也便于人审和模型处理。官方 Slides，p.14–15、22

Skill 也需要评测。第 26 页展示了超过 100 道性能题的结果：Brendan2015 为 17.4%，perf1 为 41.3%，perf2 为 79.8%；Brendan2015B 的 86.2% 被作者明确标为 Invalid，并用于说明 AI 可能找到提高评测分数的投机路径。阅读这张表时，需同时记录分数与有效性标记。官方 Slides，p.26

本文建议：把诊断经验写成可版本化的过程，包含适用问题、所需证据、工具、停止条件和结论格式；评测中独立检查根因、取证链和任务完成条件，并保留失败样例。观测预算也应纳入模型处理成本。

5.2 drgn + MCP：让模型按证据决定下一次查询

Red Hat 的 slides 展示了真实 RT 内核故障链。thr-suspended 以 SCHED_RR、优先级 1 绑定 CPU 2，在 XFS 的 xlog_cil_insert_items 中持读锁时被抢占；同 CPU 上优先级 9 的 RT 任务持续运行，使该读者无法到达解锁路径。XFS 写者等待读者计数归零，后续读者又被写者持有的 rtmutex 阻挡。官方 Slides，p.4

作者报告最终有 336 个锁等待者、约 23,000 个 D-state 任务，最后一个读者 15.8 小时未被调度，随后发生 Watchdog NMI panic。诊断关键在于把 CPU 亲和性、优先级、锁所有权和等待关系连在一起。

drgn-mcp 将调试能力接入 MCP 客户端，要求本地 vmcore 与匹配的 vmlinux；第 5 页介绍调查演示。第 3 页也明确 eval_expression 提供完整 Python 解释能力，因此部署时需要由运行环境提供权限与资源约束。官方 Slides，p.3–5

5.3 Agentic 网络观测首先是系统工程

腾讯的未排期提案明确把轻量透明的框架、高质量数据和强隔离环境列为引入 AI 推理前的条件。官方提案

本文判断：底层观测系统与通用 Agent 平台可以结合，让模型在权限、资源和执行约束内按需取证。故障诊断默认只读；提高采样强度或执行修复，需要独立的控制路径。这些控制路径需要在迁移实现中验证。

六、主线五：从“发现问题”走向“可复现、值得修、有人负责”

6.1 报告数量不是可靠性成果

What Bugs Matter? 关注异构报告的归并、子系统映射、在 KASAN 内核中尝试生成并运行 reproducer，以及实际影响评估。官方摘要

同一作者的 From Findings to Fixes 进一步介绍正在开发的持续缺陷收集与验证平台，强调验证复现条件、触发权限和实际影响，再为获得运行证据的问题生成分析和候选补丁。官方摘要两场内容相关，不宜当作两份相互独立的效果验证。

对 SRE 的启示：报警、疑似缺陷、可复现问题、值得投入的问题和已完成修复，应是不同的状态。incident 的解决状态应以修复后的实际验证结果为依据。

6.2 Syzbot：把补丁迭代和审核责任连起来

七、主线六：观测系统本身也需要可预测的控制与验证

7.1 BPF Runtime Verification：已知规则可变成在线检查

BPF RV 议题探索把确定性自动机等运行时验证逻辑映射到 BPF，利用 maps、ring buffer、struct_ops 等机制与现有 RV 框架和命令行生命周期管理整合。官方摘要

它提示了一条与大型模型互补的路线：规则明确、状态空间可控的问题，可以由专用 monitor 在线判断。本文进一步建议，把经验证的故障经验实现为轻量检测器。 monitor 的误报、漏报、事件缺失和资源消耗仍需测试。

7.2 Livepatch 与探针冲突需要生产控制

共存模型议题指出，热补丁与 ftrace、kprobe、kretprobe、BPF 等机制可能争用同一函数附近的插桩能力，造成发布阻塞或观测缺口。讨论方向包括占用报告、明确的失败原因、转换进度和负向测试。官方摘要

官方议题页与 session 议程均将该讨论排在 10 月 7 日 15:45。更新议程

SRE 含义：telemetry 并非永远安全、可忽略的旁路组件。探针本身会影响权限、时序和发布行为；自动诊断系统在增加探针、增强采样或提出 livepatch 前，应该先了解已有占用和冲突。这些系统要求还需要落实到具体接口及其稳定性验证。

7.3 CRIU + RDMA：恢复要覆盖设备状态与连接

NVIDIA 的 33 页报告给出已工作的原型：通过 CRIU 保存和恢复 RDMA 用户上下文，以及 PD、MR、CQ、RC QP 对象；在 ConnectX-7 VF 和 RXE 上实现，并验证运行中的 RDMA perftest 恢复流量。作者报告与 CUDA Checkpoint、GPU DMA-BUF 集成，最高达到 400G 线速，CPU 覆盖 x86 与 ARM。官方 Slides，p.3

关键步骤是按依赖顺序恢复对象图，保持设备镜像内 DMA 地址对应的 IOVA 稳定，并复用 vHCA 固件接口保存／加载 VF 状态、暂停／恢复数据通路。稳定 IOVA 的 DMA API 扩展仍在讨论。官方 Slides，p.15–25

第 32 页列明当前限制：RC 工作负载已验证，UD 尚不完整或未验证，UC/RD 未支持；RDMA CM、SRQ、AH、ODP 等恢复能力也有缺口，事件 FD 状态支持尚不完整。第 3 页把整理上游提交和验证真实大型训练／推理任务列为后续重点。官方 Slides，p.3、32

对 SRE 的启示：恢复能力需要覆盖进程内存、对象依赖和设备状态。大规模 AI 任务的故障恢复、容量调度和维护是它的应用方向，实际部署仍需按硬件、传输类型和外部依赖逐项验收。

九、对 Android / OpenHarmony 的迁移建议

本节给出面向设备端的概念设计，接口与成本需要在 Android / OpenHarmony 各自平台验证。

建议把系统拆成一条较短的闭环：

9.1 第一版从一种等待类故障开始

较合适的起点是 ANR / AppFreeze 的一种等待类故障：从用户可见超时窗口出发，区分主线程正在运行、可运行但没获得 CPU、等待锁、等待 IPC 或等待 I/O，然后沿实际接口可提供的依赖继续调查。

设备端优先做便宜的检测和有界采集；较重的检索、源码分析和候选修复可以放在隔离的分析环境。不要在设备已经严重卡顿时，默认启动无界扫描或高开销采集。

9.2 Evidence package 至少要说明“它没记录到什么”

下表是一份待平台实现与验证的数据契约。

信息 目的
构建身份、内核版本、必要配置和符号／BTF 对应关系 避免用错误布局解释内存或栈
启动标识、对象标识及生命周期／代次信息 减少跨启动或地址复用导致的错误关联
时间源、采集开始／结束时间、必要的时钟映射 明确跨线程、跨来源的时间关系
触发原因、采集器版本和有效观测窗口 让证据可追溯
丢弃计数、截断标志、预算耗尽、不可访问字段 让分析器识别信息缺口
用户症状、栈、任务状态及可获取的等待依赖 把系统状态连接到具体故障
事实、派生结果、模型假设分别存放 避免模型推断被后续系统误当成原始证据

对敏感数据还应有明确的脱敏和访问范围。内存、用户标识和业务载荷的采集与上传，应遵循具体授权和数据最小化要求。

9.3 用故障库评价“少记录是否仍然够用”

要验证稀疏记录方案，可以从已知根因、已有修复及可重复触发的故障样例开始，对比不同采集预算下的诊断结果。评价目标不只是正确答案比例，还包括错误高置信结论、需要补采的比例、未知问题的保留能力，以及设备端的 CPU、内存、延迟和电量开销。

这样的试验才能回答：“减少的那些数据，是否真的没有诊断价值？”采集策略的有效性应由这套可重复试验判断。

十、让证据能力与验证范围对应

快照描述状态，回放还需要执行条件。 快照描述某段采集窗口内的状态；完整执行回放还依赖输入、调度、外部状态与非确定性来源。filtered dump、live snapshot、checkpoint 和 deterministic replay 应分别说明能力。

相关线索需要因果验证。 时间线和依赖关系缩小候选范围，结论还要接受反例、复现或干预检验。缺失信息保留为未知，模型推断单独标识。

有界采集需要实际测量。 静态开关、BPF verifier 和遍历限额提供约束，目标工作负载上的测量说明实际扰动，尤其要覆盖极端负载。

自动生成的结果需要独立检查。 诊断脚本、检测规则和补丁分别通过相应验证，观察、测试、修改和部署权限按职责设置。

对于低开销设备观测，可以从少量长期线索、触发式状态采集、依赖关联和按需诊断逐步建立闭环。目标是预算内的诊断充分性：保留有身份、有时间、有范围、能够支持检验的证据，并持续验证观测和修复的实际效果。
